MoodMate agentic flow

How to take a piece of work from an idea in your head to code running in production, using Claude Code skills in this repo. One main session drives it; a subagent is used only where it isolates noisy work.

The main flow, step by step

Keep steps 1–3 in one unbroken session. Don't /clear or /compact until the tickets exist, so the spec and tickets build on the same thinking as the interview.
1

Sharpen the idea: /grill-with-docs

Say what you want in a sentence or two. Claude interviews you one question at a time until every decision is settled. Facts it looks up in the code itself; decisions it asks you about.

Produces CONTEXT.md glossary terms, ADRs in docs/adr/You do answer questions, push back
/grill-with-docs let users export their mood history as CSV from the history page
2

Write it down: /to-spec

Turns the conversation into a spec and publishes it as a GitHub issue. If the spec relies on claims about how existing code behaves, ask for a plan challenge: a fresh read-only agent verifies each claim against the code and reports blockers, gaps and what it confirmed.

Produces a spec issue on GitHub
/to-spec
then: challenge this spec with a fresh Plan agent before we slice it
3

Slice it: /to-tickets

Splits the spec into tracer-bullet tickets. Each ticket is a thin vertical slice (route → service → repository → client service → UI) that works end to end on its own, with blocking links between tickets.

Produces GitHub issues labelled ready-for-agent, with native "blocked by" links
4

Build each ticket: /implement

See the per-ticket loop below. Pick any ticket whose blockers are closed.

Shipping to production

Merging to main is the deploy. Run /ship when the tickets are done and committed. It stops and asks before the one step you can't undo.

/ship
StepWhat /ship does
1. PreflightChecks you're on a feature branch, up to date with main, and runs lint + tests for whichever of server/client changed
2. PRPushes and opens a PR to main with Closes #n for the tickets
3. CIWaits for ci.yml. If it's red: reads the log and fixes or reports. Never merges on red.
4. Merge gateAsks you, naming what will deploy (backend, frontend, or both)
5. DeployWatches cd-backend.yml (ECR → EC2) and/or cd-frontend.yml (S3 → CloudFront)
6. SmokeChecks prod /health, then runs ui-tester read-only on the changed screens
7. If smoke failsAsks: revert PR, fix forward via /diagnosing-bugs, or leave it
Needs the GitHub CLI. Install it with winget install --id GitHub.cli, then type ! gh auth login in Claude Code. The issue tracker skills need it too. On first run, /ship asks for your production URLs and saves them in docs/agents/deploy.md.

Context hygiene

Claude reasons best in roughly the first ~150k tokens of a session. Decide what to do with the context at a phase boundary (after grilling, after tickets, between tickets), never mid-phase.

OptionUse when
ContinueThe next phase genuinely needs what's in context now (e.g. grill → spec → tickets)
/clearNothing here matters to what's next. Between tickets, every time.
/compactThe default when you're getting long but still need the gist
SubagentA bounded side task whose output is noisy, like browser testing or a wide code search
/handoffMoving to another directory, harness or person (e.g. going off to a prototype)

Rules of thumb

  • Don't skip the grilling. Ambiguity that survives it shows up later as rework.
  • One ticket per session. /clear between them.
  • A ticket is a vertical slice, not "the backend part" or "the frontend part".
  • "It compiles" is not "it works". Trust tests and observed browser behaviour, not code that looks right.
  • Claude never merges or pushes to main unasked. Merging is the deploy.
  • Edit docs/agents/*.md directly to change conventions; no need to re-run setup.
